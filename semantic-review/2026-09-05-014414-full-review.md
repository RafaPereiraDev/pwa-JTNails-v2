# Revisão de segurança e qualidade — Tainara Nails

O sistema é um painel de gestão de salão de manicure em Node.js/Express com PostgreSQL e frontend vanilla. O padrão de queries é sólido (parameterizado via `pg`, sem concatenação de strings), mas há falhas de autorização que permitem leitura cruzada entre profissionais, uma race condition na criação de agendamentos públicos, e uma limpeza automática de histórico que pode destruir dados financeiros permanentemente e sem aviso.

**Watch for:** (1) Profissional consegue ler dados de outras profissionais em múltiplos endpoints — *confirmed*. (2) Race condition no agendamento público — dois clientes simultâneos gravam no mesmo horário — *confirmed*. (3) `cleanOldHistory` deleta transações de receita de agendamentos antigos silenciosamente, sem backup e sem transação — *confirmed*. (4) Caminho `isMaster` em `transactions.js` nunca executa — o master está bloqueado antes dos handlers — *confirmed*.

**Verdict**: NEEDS_CHANGES

---

## High-level view

A autenticação JWT falha em startup se `JWT_SECRET` não estiver definido, e `authenticateToken` protege todas as rotas privadas corretamente. O problema está na autorização pós-autenticação: uma profissional com token válido pode chamar `GET /api/clients/` e ver toda a base de clientes do salão, `GET /api/appointments/` sem filtro forçado pelo servidor em algumas rotas de reports, e `GET /api/professionals/` com dados internos de todas. A decisão de permitir ou não esse acesso precisa ser explícita — hoje é omissão.

O endpoint público `POST /api/public/appointments` verifica conflito de horário e insere em queries separadas sem transação. Dois requests simultâneos para o mesmo slot passam pela checagem antes de qualquer insert e ambos gravam — double-booking confirmado. O endpoint autenticado `POST /api/appointments` tem o mesmo problema via `hasConflict`.

`cleanOldHistory` deleta transações financeiras vinculadas a agendamentos com mais de dois meses, sem transação e sem log granular. Para um salão com obrigação de histórico fiscal, perder receitas antigas é um risco real — e hoje acontece silenciosamente.

Em `transactions.js`, o `router.use` do topo bloqueia o role `master` com 403. Os handlers abaixo verificam `isMaster = req.user.role === 'master'` para montar a visão consolidada por profissional — esse caminho nunca executa. O frontend recebe `by_professional: []` sempre.

<summary>Issues (11)</summary>

1. **Leitura cruzada de clientes e agenda** — `GET /api/clients/` e `GET /api/clients/:id` não têm filtro por profissional nem `requireAdmin`. Qualquer role `professional` vê toda a base de clientes com telefone, e-mail e histórico. Decidir se é intencional; se não for, adicionar filtro ou `requireAdmin`.

2. **Leitura cruzada em relatórios** — `GET /api/reports/dashboard` usa `profId = req.user.role === 'master' ? null : req.user.professional_id`; um admin sem `professional_id` recebe `null` e vê dados globais sem filtro. `GET /api/reports/appointments` tem assimetria idêntica. Documentar ou corrigir.

3. **Race condition no agendamento público** — `POST /api/public/appointments` verifica conflito e insere em queries separadas. Dois requests simultâneos para o mesmo slot passam pela checagem ao mesmo tempo e ambos gravam. Envolver em `withTransaction` com `SELECT ... FOR UPDATE` na tabela de agendamentos do profissional/data.

4. **Race condition no agendamento autenticado** — `POST /api/appointments` tem o mesmo problema: `hasConflict` e o insert são queries separadas sem transação.

5. **`cleanOldHistory` não transacional** — deleta transações e depois agendamentos em duas queries separadas. Se o processo morrer entre elas, as transações de receita foram perdidas mas os agendamentos ainda existem. Envolver em `withTransaction` e logar a contagem de transações deletadas.

6. **Caminho `isMaster` morto em `transactions.js`** — o `router.use` bloqueia master com 403; `isMaster = req.user.role === 'master'` nos handlers abaixo é sempre `false`. O `byProfessional` do summary nunca é populado. Decidir: se master não deve acessar financeiro, remover o código morto; se deve, remover o 403.

7. **`SELECT *` no login expõe o hash da senha no objeto em memória** — `auth.js` faz `SELECT *` de `users` e o objeto resultante (com `password`) fica em memória até o GC. Qualquer `console.error(user)` ou serialização acidental vaza o hash. Trocar para colunas explícitas sem `password`.

8. **`bcrypt.hashSync` bloqueia o event loop** — `professionals.js` e `users.js` usam `bcrypt.hashSync(password, 10)` em handlers async. Com cost factor 10, cada chamada bloqueia o event loop por ~100ms. Trocar por `await bcrypt.hash(password, 10)`.

9. **Validação de formato ausente no agendamento autenticado** — `POST /api/appointments` e `PUT /api/appointments/:id` não validam formato de `date` (YYYY-MM-DD) nem de `start_time` (HH:MM). O endpoint público valida; o autenticado não. `start_time` malformado faz `calcEndTime` retornar `NaN:NaN` que é inserido no banco.

10. **`PUT /api/professionals/:id` não valida email** — o `POST` valida o formato; o `PUT` não. O email é sincronizado para a tabela `users`, então um email malformado pode impedir o login da profissional.

11. **`rejectUnauthorized: false` no SSL do banco** — `db.js` usa `ssl: { rejectUnauthorized: false }` para qualquer URL não-localhost. Em produção no Render, a verificação do certificado do banco está desabilitada. Usar o CA fornecido pelo Render ou documentar o risco explicitamente.

### Leitura cruzada de dados entre profissionais

Em `clients.js`, `GET /` e `GET /:id` requerem apenas `authenticateToken`. Uma profissional com role `professional` lista toda a base de clientes do salão — nome, telefone, e-mail, notas, e até o histórico completo de agendamentos de `GET /:id`. Não há filtro por `professional_id` nem verificação de role.

Em `appointments.js`, `GET /` força `prof = req.user.professional_id` quando o role é `professional` — correto. Mas `GET /api/reports/appointments` em `reports.js`:

```js
let prof = professional_id;
if (req.user.role !== 'master' && req.user.professional_id)
  prof = req.user.professional_id;
```

Se `req.user.professional_id` for `null` (admin sem vínculo de profissional), a condição é falsa e `prof` recebe o `professional_id` da query string — ou fica `undefined`, exibindo todos os agendamentos sem filtro. Em `reports/dashboard`, um admin sem `professional_id` cai no ramo `null` e vê dados globais do salão sem filtro de profissional.

### Race condition no agendamento público e autenticado

`POST /api/public/appointments` executa:

```
1. SELECT conflito de appointment
2. SELECT conflito de blocked_time
3. SELECT/INSERT client
4. INSERT appointment
```

Nenhum desses passos está dentro de uma transação. Dois requests para o mesmo slot chegam simultaneamente, ambos passam pelos passos 1 e 2 antes de qualquer insert, e ambos executam o passo 4 — double-booking. O endpoint autenticado `POST /api/appointments` tem o mesmo problema: `hasConflict` chama duas queries separadas e o insert fica fora de qualquer transação.

### `cleanOldHistory` — deleção não transacional de dados financeiros

```js
const txRes   = await dbQuery('DELETE FROM transactions WHERE appointment_id IN ...', [cutoff]);
const apptRes = await dbQuery('DELETE FROM appointments WHERE date < $1', [cutoff]);
```

As deletes não estão em transação. Se o processo for interrompido entre elas, as transações de receita desaparecem mas os agendamentos continuam existindo — inconsistência silenciosa. Além disso, o log atual só imprime quando `deleted > 0` na contagem de agendamentos, sem nunca mencionar quantas transações de receita foram removidas.

### Caminho `isMaster` morto em transactions.js

```js
router.use(authenticateToken, (req, res, next) => {
  if (req.user.role === 'master')
    return res.status(403).json({ error: '...' });
  next();
});

// em GET /summary — nunca alcançado por master:
const isMaster = req.user.role === 'master'; // sempre false
const byProfessional = isMaster ? await getAll(...) : []; // sempre []
```

O `byProfessional` no payload de `/summary` é sempre `[]`. O frontend que renderiza a visão consolidada de faturamento por profissional nunca recebe os dados reais.

### `rejectUnauthorized: false` no pool PostgreSQL

```js
ssl: process.env.DATABASE_URL?.includes('localhost')
  ? false
  : { rejectUnauthorized: false },
```

Para qualquer URL de produção (Render, Railway, etc.), o SSL está ativo mas sem verificação do certificado do servidor de banco. Um MITM entre o container Node e o banco consegue interceptar todas as queries. O Render disponibiliza o certificado CA do banco de dados — a configuração correta é `ssl: { rejectUnauthorized: true, ca: process.env.DATABASE_CA }`.

### `bcrypt.hashSync` bloqueando o event loop

`professionals.js` e `users.js` usam `bcrypt.hashSync` dentro de handlers `async`. O bcrypt síncrono com cost factor 10 executa ~100ms de CPU pura no thread principal do Node. Durante esse tempo, nenhum outro request é processado. Em produção, criar ou atualizar um usuário degrada todas as requisições simultâneas. Trocar por:

```js
const hash = await bcrypt.hash(password, 10);
```

### Validação ausente em agendamentos autenticados

`POST /api/appointments` e `PUT /api/appointments/:id` não validam `date` nem `start_time`. O endpoint público tem:

```js
if (!/^\d{4}-\d{2}-\d{2}$/.test(date) || !/^\d{2}:\d{2}$/.test(start_time))
  return res.status(400).json({ error: 'Data ou horário inválidos' });
```

O autenticado não. `calcEndTime('abc', 60)` retorna `NaN:NaN` que vai para o banco como `end_time`. Queries posteriores que comparam `start_time < $3 AND end_time > $4` com esse valor geram erro ou comportamento indefinido.

### `PUT /api/professionals/:id` sem validação de email

O `POST` em `professionals.js` valida:
```js
if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email))
  return res.status(400).json({ error: 'E-mail inválido' });
```

O `PUT` não tem esse guard. Como o email é sincronizado para a tabela `users` (`UPDATE users SET email=$2 WHERE id=$4`), um email malformado sobrescreve o login da profissional — potencialmente bloqueando o acesso ao painel.
